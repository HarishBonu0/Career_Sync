## 3. Input/Output Contract
**Input:** The authenticated User ID (from `req.user.id`) and a deterministic `targetRole` string identifier.
**Output:** A securely derived `SkillGapAnalysis` result including `matchedSkills`, `missingSkills` (and placeholder `partialSkills`), retaining original `evidence` directly referenced from the user's `SkillProfile`.

## 4. Target-Role Contract
Role requirements are defined purely in a static local registry (`config/targetRoles.js`). The registry is deterministic, small, explicitly defined, and does NOT depend on LLMs, embeddings, or external job scraping APIs. Unknown target roles are rejected safely.

## 5. Matching Rules
Matching relies strictly on canonical string equality (`===`). There is no substring matching (e.g. React Native does not match React). `Java` != `JavaScript`. No LLM semantic similarity is employed.

## 6. Classification Rules
- **MATCHED**: Canonical names match perfectly AND there is at least one valid evidence block in the user's `SkillProfile`.
- **PARTIAL**: Left empty to avoid false optimism, as no equivalence mapping exists yet.
- **MISSING**: Canonical name is completely absent, OR the user possesses the skill but evidence is invalid/empty.

## 7. Evidence Rules
Matched evidence is strictly preserved and copied over directly from `SkillProfile`. No explanatory text is generated by Phase 5C. Raw resume text is NOT accessed by Phase 5C. 

## 8. Proficiency Rules
Phase 5C does not calculate, invent, or aggregate proficiency based on years of experience, frequency of evidence, or job titles. Explicit proficiency inherited safely from Phase 5B remains preserved as-is.

## 9. Persistence/Idempotency
Gap Analysis results are persisted to `SkillGapAnalysis` uniquely scoped by `{ user, targetRoleId }`. Running the analysis multiple times gracefully overwrites the single derived result for that role rather than inflating duplicate records. `SkillProfile` is treated as strictly read-only and never mutated.

## 10. Authentication/Ownership
All gap analysis API routes are protected by JWT auth (`req.user.id`). Client-side payload IDs are ignored. Cross-user data leakage is systematically prevented by MongoDB queries scoped exactly to the authenticated user.
